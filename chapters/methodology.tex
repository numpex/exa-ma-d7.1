\chapter{Software Production and Benchmarking Methodology (D7.1)}
\label{chap:methodology}

The unit of comparison is a campaign for a specified application, solver
or kernel. \Cref{chap:software} identifies the implementation and its
supported configurations. The application fiche describes the test
problem, and \Cref{tab:v3-benchmark-registry} gives the stage reached by
each registered benchmark.

\section{Application categories}
\label{sec:benchmark-application-categories}

\begin{description}
  \item[Mini-app] A focused test of a method or kernel.
  \item[Extended mini-app] A mini-app with supporting workflows, such as
    preparation of input data or I/O tests.
  \item[Demonstrator] An integrated scientific workflow drawing on several
    work packages.
  \item[Proxy-app] A representative workload combining components from
    three or more work packages for a system-level study.
\end{description}

The Ktirio Urban Building demonstrator, for example, combines meshing,
coupling and ensemble processing. The reported terrain-generation
benchmark measures the meshing component
(\cref{sec:pc5:ktirio-urban-building,sec:app:specs:app-feelpp-ktirio-geom}).

\section{Verification, validation and scaling}
\label{sec:benchmark-protocol}

Verification compares the computation with a known solution, a
manufactured case or a specified reference. The thermal-bridge case
compares computed quantities with ISO~10211 reference values before
examining scaling (\cref{sec:app:specs:app-feelpp-discr-1}). Validation
uses observations when the application has suitable experimental or
field data. The FDA nozzle specification, for example, defines which
velocity and pressure quantities to compare with measurements
(\cref{sec:app:specs:app-feelpp-discr-2}). Regression tests address a
different question: whether a change in code preserves an established
behaviour.

Strong scaling fixes the problem size. Weak scaling keeps the workload
per unit of computing resource approximately constant. Comparisons use
a stated reference run and distinguish setup, solver and I/O times
where the campaign reports them. The Composyx diffusion study
(\cref{sec:app:specs:app-composyx-diffusion}) reports solver phases and
iteration counts for CUDA on Jean Zay and HIP on Adastra. Each series
uses its own one-node baseline and residual tolerance.

Energy-to-solution uses the same workload and measurement interval as
time-to-solution, with the measurement boundary stated explicitly. The
PETSc mixed-precision specification includes setup, solver, conversion
and transfer costs in its proposed comparison
(\cref{sec:app:specs:app-petsc-mixed-precision}). Energy measurements for
that comparison remain to be reported.

\section{Software and campaign records}
\label{sec:benchmark-campaign-records}

The campaign record identifies the software revision, inputs and
parameters, machine and resource counts, baseline and criterion for
accepting a solution. Repeated measurements give an indication of
variability when timings are available. The application fiches link
to the corresponding release, driver, configuration or data archive
where these are recorded. Some historical campaigns provide figures
without a complete archive of the runs.

WP7 uses versioned application repositories and software environments
to run and share benchmarks. The I/O case provides configurations and
measurement files for its reported comparisons
(\cref{sec:app:specs:app-feelpp-io}). PETSc's CUDA regression cases
document the HPDDM execution path in the released solver
(\cref{sec:HPDDM:2026}). For resilience, WP3 reports the use of in-memory
checkpoints for soft errors and VeloC disk checkpoints for crashes
(\cref{chap:wp3}). These tests and measurements address distinct
parts of software and application readiness.
