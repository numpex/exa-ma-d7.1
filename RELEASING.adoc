= Release preparation

Release preparation updates local metadata and produces reviewable PDFs.
It does not authorize a commit, tag, push or publication. Follow the review
requirements in `AGENTS.md` before those steps.

== 1. Confirm the checkout and current version

The installed command follows the `exa-ma-harvest` naming convention used in
the shared Exa-MA tools repository. Its implementation remains in this checkout.
Install with Python 3.11 or newer:

[source,shell]
----
uv tool install --python 3.11 --editable .
----

`exama-version` is an equivalent command alias. Neither command creates releases
in another repository implicitly. The default is the current checkout (including
when invoked from a subdirectory); select another checkout explicitly with
`exa-ma-version --repo /absolute/path/to/checkout check`.
Without installation, use
`uv run --no-project --python 3.11 python scripts/release.py` with the same arguments.

[source,shell]
----
git rev-parse --show-toplevel
git branch --show-current
git status --short
exa-ma-version check
----

The check prints the absolute checkout path and the selected main TeX file.
It prefers `exa-ma-deliverables.tex` when present and otherwise uses the legacy
`exa-ma-d7.1.tex`. The active document version and `pyproject.toml` must agree;
generated standalone identity data, active cover/PDF/WP titles, current registry
and training introductions, and the local project entry in `uv.lock` (when present)
must also carry that same version.
Versions are specific to a checkout: a sibling worktree can be ahead.

The version printed on a fiche is explicitly the *deliverable version*.
It is not the version of Feel++ or another software package.

== 2. Refresh requested catalogue entries

Refresh the relevant local CSV snapshots from their identified sources.
Preserve unrelated records, scientific claims and benchmark results.
Record the snapshot provenance, including relevant cell notes.
Do not refresh the bibliography as an incidental consequence of a metadata edit.
If bibliography changes are part of the release, refresh them explicitly and
inspect that diff separately.

[source,shell]
----
uv run --no-project --python 3.11 --with 'jinja2>=3.1,<4' python gen.py --framework feelpp
uv run --no-project --python 3.11 python scripts/sync_applications.py --standalone
uv run --no-project --python 3.11 python scripts/generate_fiche_identities.py
----

== 3. Prepare the version bump

Choose an explicit version `X.Y.Z`, or a prerelease such as `X.Y.Z-rc.N`.
Use a patch for corrections, a minor version for substantial compatible
content additions, and a major version for a major restructuring.
The example below is a template; replace `X.Y.Z`, authors and summary before running it.

[source,shell]
----
# Dry run: list the proposed metadata changes without writing.
exa-ma-version bump X.Y.Z --diff \
  --authors "Release authors" --summary "Concrete changes in this release"

# Apply the reviewed local metadata plan.
exa-ma-version bump X.Y.Z \
  --authors "Release authors" --summary "Concrete changes in this release" --write

git diff --check
git diff
----

Preparation synchronizes `pyproject.toml`, the local project version in `uv.lock`,
active main-document title and version, standalone WP title metadata, current
registry/training release mentions, actual date and a new top changelog entry.
It regenerates standalone identity data. If generation or final consistency
validation fails, the original release metadata is restored.
Dependency versions in the lockfile are
preserved; a release bump does not perform a dependency upgrade.
Historical changelog entries,
contractual dates, final-target versions and scientific content are preserved.
It rejects non-increasing or malformed versions and mismatched current metadata.

Check draft/final/submitted status, cover wording, release notes, remaining
editorial version mentions and pending contributions separately. These are
editorial decisions rather than automatic consequences of a version bump.

[cols="1,3",options="header"]
|===
|Identifier |Role
|Main TeX `\delivVersion` |Authoritative deliverable version; must match the package version.
|`pyproject.toml`, local `uv.lock` entry |Package and local environment identity; synchronized by `bump`.
|Cover, PDF metadata, WP titles, standalone identity data |Visible release labels; updated or regenerated by `bump`.
|Changelog and release notes |A new changelog entry is added; historical records are retained. Write release notes for the chosen version explicitly.
|Git tag and commit |Publication identity. CI requires the publication tag to match the declared version. Preparation never creates either.
|`gitHeadLocal.gin`, `.git/gitHeadInfo.gin` |Build-derived Git provenance, refreshed by hooks/article-cli. They can describe an older tag in a dirty working tree; never rewrite them as version constants.
|===

== 4. Validate and review

[source,shell]
----
exa-ma-version check
uv run --no-project --python 3.11 python scripts/generate_fiche_identities.py --check
uv run --no-project --python 3.11 python scripts/sync_applications.py --standalone --check
uv run --no-project --python 3.11 --with 'jinja2>=3.1,<4' --with 'openpyxl>=3.1,<4' \
  --with pytest python -m pytest tests/test_gen.py tests/test_release.py tests/test_fiche_identities.py -q

# Use the main filename printed by exa-ma-version check.
# This checkout uses exa-ma-d7.1.tex; newer layouts may use exa-ma-deliverables.tex.
latexmk --shell-escape -pdf -interaction=nonstopmode -synctex=1 exa-ma-d7.1.tex
latexmk --shell-escape -pdf -interaction=nonstopmode -synctex=1 \
  -outdir=output/pdf standalone/feelpp.tex
----

Inspect logs as well as exit status. Resolve undefined citations/references,
missing assets and LaTeX errors; distinguish inherited layout warnings from
regressions. Review affected PDF pages, fiche identity panels, internal section
links, bibliography links and external URL targets.

== 5. Commit and publish only after explicit authorization

Review `AGENTS.md`, the complete diff, generated outputs and validation evidence
with the maintainer. Stage only the approved files; avoid a blanket add.
After explicit authorization, commit the reviewed changes and create an
annotated `vX.Y.Z` tag on that exact commit, then push the approved branch/tag.
The release workflow can then publish the PDF and release assets.

Before publishing, run `exa-ma-version check --tag vX.Y.Z`. CI performs that
same tag/version check on tag builds and refuses a mismatched release. After
tagging, verify `git describe --exact-match --tags HEAD` identifies the expected
tag, rebuild, and inspect the PDF's Git provenance/footer as well as its cover.

The manual tag path keeps publication separate from preparation.
`article-cli create` also commits release metadata, so use it only when that
extra commit is intended and authorized; rebuild/recheck if it changes inputs.
Do not delete or replace an existing published tag as a routine version bump.
