\subsection{Software summary}
\label{sec:Zellij:summary}

This specification describes Exa-Zellij at commit
\href{https://github.com/MehdielKhadiri/Exa-Zellij/tree/eddc639b034b0ca26f145c407f398e908e5b4498}{\texttt{eddc639b034b0ca26f145c407f398e908e5b4498}}.

Exa-Zellij is a C++ implementation using MPI and Kokkos, with a Python
interface. It builds on the modular fractal-decomposition approach of the
\href{https://github.com/ThomasFirmin/zellij}{Zellij framework}
and extends it to configurable FBD and FBO algorithms for heterogeneous HPC
systems. The PFDA-BS, ASTRA-FBO and TriFBO-KV work presented in WP5 uses
Exa-Zellij.

Exa-Zellij is a configurable implementation of two related families
for bounded continuous black-box optimization: Fractal-Based Decomposition
(FBD) and Fractal Bayesian Optimization (FBO). Both organize the decision
space as a hierarchy of self-similar fractals. FBD allocates work through its
geometry and structural controls, whereas FBO uses a global objective-call
budget together with surrogate and acquisition information.

The FBD family exposes five independent runtime components:
decomposition geometry, exploration, scoring, tree search and exploitation.
The FBO family additionally exposes the initial design, surrogate and
kernel,
acquisition-guided selection, budget allocation and exploitation strategy.
The effective configuration and actual evaluation count are reported for
every run.

The implementation retains this component-oriented philosophy while
making it directly usable as software: users select a family and its
components at runtime, supply a native, Python, batched, embedded-module or
executable objective, and keep the optimizer independent of application-side
simulation code.

\subsection{Purpose}
\label{sec:Zellij:purpose}

Exa-Zellij implements divide-and-conquer optimization through a
hierarchical decomposition of the search space. Independent child fractals
expose independent objective evaluations, while a configurable selection
rule
determines which fractals will be decomposed next. The framework targets
high-dimensional and expensive objectives for which gradients are
unavailable,
unreliable or too costly.

This software framework has been inspired by two distinct families of
decomposition-based optimization algorithms. The first one is based on
algorithms derived from Lipschitzian global optimization, such as DIRECT
and its various extensions (e.g. eDIRECT, BIRECT, HD-DIRECT). The second
one concerns metaheuristics based on fractal decomposition, such as
FRACTOP and FDA.

Four properties characterize the current Exa-Zellij implementation:
\begin{itemize}
\item \textbf{Generalization}: our goal is to build a framework which
unifies configurable FBD and FBO families in one runtime. The current
component matrix includes six decomposition geometries and interchangeable
exploration, scoring, tree-search, surrogate, kernel, budget and
exploitation
choices.

\item \textbf{Modularity}: the framework must be as modular as possible,
so algorithms can be assembled from explicit components and objectives
can be replaced without editing the optimizer. Python callbacks, batched
callbacks, JSON configurations, executable adapters and embedded Python
modules expose the same optimization core.

\item \textbf{Massively parallel}: a transparent and efficient parallel
implementation uses MPI to distribute independent fractal work and
Kokkos to target CPU, NVIDIA CUDA and AMD HIP execution spaces. Scalar and
batched objective boundaries keep application evaluation separate from tree
selection and compact global reductions.

\item \textbf{Resilience and reproducibility}: checkpoints save the active
fractals, the best solution and the evaluated points and their values after
a completed search depth. Checksums detect damaged files; backup copies
and earlier checkpoints provide alternative recovery files. Restart can
use the same or a different number of MPI processes. Seeds, tests and
result-verification material support reproducible runs. The tested
configurations are listed below.
\end{itemize}

\subsection{Tested configurations}
\label{sec:Zellij:validation}

The test records included in this commit cover the following configurations.

\begin{itemize}
\item \textbf{CPU and user interfaces.} Linux x86-64/WSL builds with GCC
11.4 and Kokkos 4.5.01 passed CPU solver and Python API tests. A Python 3.12
wheel was built, installed and exercised. Tests cover both families,
scalar and batched callbacks, external executable objectives and the JSON
command-line interface. See \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/docs/validation.md}{the validation report}.

\item \textbf{MPI on CPU.} Open MPI 5.0.6 with Python 3.12 and pybind11
3.0.1 passed five CTest groups, including two-process runs of both FBD and
FBO with native analytic and embedded Python objectives. The tests check
the objective value at the returned solution. See \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/docs/validation.md}{the validation report} and \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/tests/test_mpi.py}{the MPI test}.

\item \textbf{MPI and CUDA on JUPITER.} Both families passed four-process
runs on one ARM-based Booster node with four NVIDIA GH200 GPUs, using
CUDA 13, Kokkos 4.7.03 and ParaStationMPI 5.13.0-1-mt. With the native
analytic objective, GPU execution covers optimizer kernels and objective
evaluations. The additional embedded Python test uses a CPU NumPy
objective and checks its integration with the CUDA optimizer. All four
returned point/value checks passed. See \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/docs/validation.md}{the validation report} and \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/scripts/jupiter/smoke.sbatch}{the JUPITER test}.

\item \textbf{MPI and HIP on LUMI-G.} The included VQE results use one MPI process
per AMD MI250X GPU die, with eight processes per node and configurations
up to 1,000 nodes and 8,000 processes. GPU execution covers both the
optimizer kernels through Kokkos/HIP and the VQE objective through
PennyLane/JAX. See \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/docs/lumi-g.md}{the LUMI-G configuration}, \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/reproducibility/lumi_g/results/strong_scaling.csv}{the scaling results} and \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/reproducibility/lumi_g/raw_evidence/log_excerpts.txt}{the execution records}.
These tests cover the VQE research configuration.

\item \textbf{Restart with a different MPI process count.} Exa-Zellij
loads checkpoints and redistributes saved points through
\texttt{--ft-elastic-resume}; see \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/src/main.cpp\#L3776-L4028}{the restart implementation}.
Both families passed restarts from 100 to 200 processes and from 200 to 100
on JUPITER, with three seeds. See \href{https://github.com/MehdielKhadiri/Exa-Zellij/blob/eddc639b034b0ca26f145c407f398e908e5b4498/docs/validation/jupiter-restart.md}{the restart test results}.
\end{itemize}

\subsection{Mathematics}
\label{sec:Zellij:mathematics}

Optimizing a non-linear, non-convex, derivative-free or black-box
function in a high-dimensional continuous search space is a complex
task. Commonly, we consider a minimization problem for an objective
function ${f: \mathcal{S} \subset \mathbb{R}^n \rightarrow \mathbb{R}}$:
\begin{equation}
\label{eq:minproblem}
   \hat{x} \in \arg\min_{x \in \mathcal{S}} f(x).
\end{equation}
Here, $\hat{x}$ is a global optimum, $f$ is the objective function, and
$\mathcal{S}$ is a compact set defined by constraints such as upper and
lower bounds on the search space.

FBD determines its number of evaluations from the selected geometry,
depth, beam, exploration and exploitation components. FBO instead receives a
global objective-evaluation budget and reports the actual evaluations
consumed
by its initial design, tree exploration and terminal exploitation. This
distinction is part of the public configuration contract.
